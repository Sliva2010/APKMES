# Requirements Document

## Introduction

**NOCTIS** — премиальный кроссплатформенный мессенджер для iOS и Android, выполненный в строгой чёрно-белой эстетике. Продукт ориентирован на пользователей, ценящих минимализм, скорость и приватность. Мессенджер поддерживает регистрацию по номеру телефона и электронной почте, обмен личными сообщениями в реальном времени, голосовые и видеозвонки, исчезающие сообщения, секретные чаты со сквозным шифрованием и более 100 продуманных функций для повседневной коммуникации.

Технический стек включает Flutter (Dart) для мобильных клиентов, Go (Fiber + WebSocket) для бэкенда, PostgreSQL для постоянного хранения и Redis для presence/pub-sub. Развёртывание производится на VPS (Ubuntu 22, IP 79.137.162.27) через Docker и Nginx с автоматизацией через GitHub Actions, который собирает Android APK и публикует его в GitHub Releases при пуше в ветку `main`.

Документ описывает требования к функционалу, дизайну, безопасности, производительности и инфраструктуре в соответствии с шаблонами EARS и правилами качества INCOSE.

## Glossary

- **NOCTIS_App**: Мобильное приложение мессенджера на Flutter (iOS и Android клиент).
- **NOCTIS_Backend**: Серверное приложение на Go, обслуживающее REST и WebSocket API.
- **Auth_Service**: Подсистема `NOCTIS_Backend`, отвечающая за регистрацию, авторизацию и управление сессиями.
- **Messaging_Service**: Подсистема `NOCTIS_Backend`, отвечающая за маршрутизацию и хранение сообщений.
- **Presence_Service**: Подсистема `NOCTIS_Backend`, отслеживающая онлайн-статусы и индикаторы набора текста.
- **Media_Service**: Подсистема `NOCTIS_Backend`, отвечающая за загрузку, хранение и выдачу медиафайлов.
- **Call_Service**: Подсистема `NOCTIS_Backend`, отвечающая за сигналинг WebRTC голосовых и видеозвонков.
- **Crypto_Module**: Клиентский модуль `NOCTIS_App`, реализующий сквозное шифрование (X3DH + Double Ratchet).
- **UI_Engine**: Слой отображения `NOCTIS_App`, отвечающий за рендеринг, анимации и микроинтеракции.
- **Theme_Engine**: Подсистема `UI_Engine`, управляющая монохромными темами (Pure Black, Pure White, Graphite, Paper).
- **Notification_Service**: Подсистема `NOCTIS_Backend`, доставляющая push-уведомления через APNs и FCM.
- **CI_Pipeline**: Конвейер GitHub Actions, выполняющий сборку, тестирование и публикацию артефактов.
- **Provision_Script**: Bash-скрипт для подготовки чистого VPS Ubuntu 22 к развёртыванию `NOCTIS_Backend`.
- **Direct_Chat**: Личный чат между двумя пользователями `NOCTIS_App`.
- **Secret_Chat**: Чат со сквозным шифрованием, привязанный к конкретному устройству, без хранения открытого текста на сервере.
- **Disappearing_Message**: Сообщение с TTL, удаляемое у всех участников по истечении срока.
- **Smart_Tag**: Метка, автоматически или вручную присваиваемая чату или сообщению для категоризации и поиска.
- **Mini_Tool**: Встроенный инструмент мессенджера (калькулятор, конвертер валют, таймер, переводчик и т. п.), доступный без выхода из чата.
- **APK_Artifact**: Файл `noctis-release.apk`, собранный `CI_Pipeline` и опубликованный в GitHub Releases.
- **Monochrome_Palette**: Палитра приложения, состоящая исключительно из оттенков серого от `#000000` до `#FFFFFF`.

## Requirements

### Requirement 1: Регистрация по номеру телефона

**User Story:** Как новый пользователь, я хочу зарегистрироваться по номеру телефона с подтверждением через SMS, чтобы быстро получить доступ к мессенджеру без пароля.

#### Acceptance Criteria

1. WHEN пользователь вводит номер телефона в формате E.164 и нажимает «Продолжить», THE Auth_Service SHALL отправить одноразовый код из 6 цифр на указанный номер в течение 5 секунд.
2. WHEN пользователь вводит корректный код подтверждения в течение 300 секунд после отправки, THE Auth_Service SHALL создать учётную запись и вернуть пару из access-токена (срок жизни 3600 секунд) и refresh-токена (срок жизни 2592000 секунд).
3. IF пользователь вводит некорректный код подтверждения, THEN THE Auth_Service SHALL вернуть ошибку `INVALID_OTP` и увеличить счётчик попыток для данного номера.
4. IF счётчик неуспешных попыток ввода кода для одного номера достигает 5 в течение 600 секунд, THEN THE Auth_Service SHALL заблокировать дальнейшие попытки для этого номера на 900 секунд.
5. WHEN пользователь запрашивает повторную отправку кода, THE Auth_Service SHALL разрешить повторную отправку не чаще одного раза в 60 секунд.
6. IF введённый номер телефона не соответствует формату E.164, THEN THE NOCTIS_App SHALL отобразить сообщение об ошибке валидации до отправки запроса.

### Requirement 2: Регистрация по электронной почте

**User Story:** Как пользователь, который предпочитает не передавать номер телефона, я хочу зарегистрироваться по электронной почте, чтобы использовать мессенджер с альтернативной верификацией.

#### Acceptance Criteria

1. WHEN пользователь вводит адрес электронной почты в корректном формате RFC 5322 и нажимает «Продолжить», THE Auth_Service SHALL отправить письмо со ссылкой подтверждения, содержащей токен со сроком жизни 1800 секунд.
2. WHEN пользователь переходит по ссылке подтверждения в течение срока действия токена, THE Auth_Service SHALL пометить адрес как подтверждённый и создать учётную запись.
3. IF введённый адрес электронной почты не соответствует формату RFC 5322, THEN THE NOCTIS_App SHALL отобразить сообщение об ошибке валидации до отправки запроса.
4. IF токен подтверждения просрочен или уже использован, THEN THE Auth_Service SHALL вернуть ошибку `EMAIL_TOKEN_INVALID` и предложить запросить новое письмо.
5. THE Auth_Service SHALL разрешить отправку повторного письма с подтверждением не чаще одного раза в 120 секунд для одного адреса.

### Requirement 3: Авторизация и управление сессиями

**User Story:** Как зарегистрированный пользователь, я хочу безопасно входить в приложение на нескольких устройствах и управлять активными сессиями, чтобы контролировать доступ к своей учётной записи.

#### Acceptance Criteria

1. WHEN пользователь успешно проходит верификацию (SMS-код или подтверждённая ссылка), THE Auth_Service SHALL создать запись активной сессии с привязкой к идентификатору устройства, модели устройства, ОС и IP-адресу.
2. WHEN access-токен истекает и клиент отправляет действительный refresh-токен, THE Auth_Service SHALL выдать новый access-токен в течение 1000 миллисекунд.
3. WHEN пользователь запрашивает список активных сессий, THE Auth_Service SHALL вернуть все записи активных сессий учётной записи с указанием устройства, ОС, IP, географической области и времени последней активности.
4. WHEN пользователь завершает выбранную сессию, THE Auth_Service SHALL инвалидировать соответствующий refresh-токен в течение 5 секунд.
5. WHEN пользователь выбирает «Завершить все сессии», THE Auth_Service SHALL инвалидировать все refresh-токены учётной записи, кроме текущего, в течение 5 секунд.
6. IF refresh-токен отсутствует в хранилище активных сессий или просрочен, THEN THE Auth_Service SHALL вернуть ошибку `SESSION_INVALID` и потребовать повторную верификацию.

### Requirement 4: Двухфакторная аутентификация по облачному паролю

**User Story:** Как пользователь, заботящийся о безопасности, я хочу установить дополнительный облачный пароль, чтобы защитить вход даже при компрометации SMS-канала.

#### Acceptance Criteria

1. WHEN пользователь устанавливает облачный пароль длиной от 8 до 64 символов, THE Auth_Service SHALL сохранить хеш пароля по алгоритму Argon2id с уникальной солью.
2. WHERE облачный пароль установлен, THE Auth_Service SHALL запрашивать его после успешной верификации SMS-кода или email-ссылки.
3. IF пользователь вводит неверный облачный пароль, THEN THE Auth_Service SHALL увеличить счётчик неуспешных попыток и вернуть ошибку `CLOUD_PASSWORD_INVALID`.
4. IF счётчик неуспешных попыток ввода облачного пароля достигает 10, THEN THE Auth_Service SHALL заблокировать вход для этой учётной записи на 3600 секунд.
5. WHERE облачный пароль установлен, THE Auth_Service SHALL разрешить его сброс только через подтверждённый email-канал восстановления.

### Requirement 5: Профиль пользователя

**User Story:** Как пользователь, я хочу управлять своим профилем (имя, никнейм, аватар, статус), чтобы контролировать, как меня видят собеседники.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL позволять пользователю задавать отображаемое имя длиной от 1 до 64 символов.
2. WHEN пользователь сохраняет никнейм длиной от 5 до 32 символов, состоящий из символов `[a-z0-9_]`, THE NOCTIS_Backend SHALL проверять уникальность никнейма и сохранять его в течение 1 секунды.
3. IF введённый никнейм уже занят другой учётной записью, THEN THE NOCTIS_Backend SHALL вернуть ошибку `USERNAME_TAKEN`.
4. WHEN пользователь загружает изображение аватара размером до 8 МБ, THE Media_Service SHALL сохранить оригинал и сгенерировать миниатюру 256×256 пикселей в течение 3 секунд.
5. THE NOCTIS_App SHALL позволять пользователю устанавливать текстовый статус длиной до 140 символов или выбирать предустановленный статус из списка.
6. WHEN пользователь скрывает номер телефона в настройках приватности, THE NOCTIS_Backend SHALL не возвращать номер телефона другим пользователям при просмотре профиля.

### Requirement 6: Управление контактами

**User Story:** Как пользователь, я хочу видеть, кто из моих контактов уже использует NOCTIS, чтобы быстро начать с ними общаться.

#### Acceptance Criteria

1. WHEN пользователь предоставляет разрешение на доступ к адресной книге, THE NOCTIS_App SHALL загружать на сервер только хеши номеров телефонов, рассчитанные по SHA-256 с фиксированной солью приложения.
2. WHEN сервер получает список хешей номеров, THE NOCTIS_Backend SHALL возвращать список найденных пользователей в течение 2 секунд для списка размером до 5000 контактов.
3. THE NOCTIS_App SHALL позволять пользователю вручную добавлять контакт по никнейму или номеру телефона.
4. WHEN пользователь удаляет контакт, THE NOCTIS_Backend SHALL удалить запись о связи в течение 1 секунды и не возвращать удалённый контакт в списке контактов.
5. WHERE пользователь не дал разрешение на доступ к адресной книге, THE NOCTIS_App SHALL разрешать поиск контактов только по никнейму.

### Requirement 7: Личные сообщения в реальном времени

**User Story:** Как пользователь, я хочу мгновенно обмениваться сообщениями с одним собеседником, чтобы вести живой диалог.

#### Acceptance Criteria

1. WHEN пользователь отправляет текстовое сообщение длиной до 4096 символов в Direct_Chat, THE Messaging_Service SHALL доставить сообщение второму участнику в течение 500 миллисекунд при условии, что оба клиента подключены по WebSocket.
2. WHEN сообщение принято сервером, THE Messaging_Service SHALL присвоить ему монотонно возрастающий идентификатор, уникальный в пределах чата.
3. WHEN получатель не подключён, THE Messaging_Service SHALL сохранять сообщение в очереди отложенной доставки до 30 суток и доставить его при следующем подключении получателя.
4. WHEN отправитель повторно отправляет сообщение с тем же клиентским идентификатором (idempotency key), THE Messaging_Service SHALL не создавать дубликат и вернуть существующий идентификатор сообщения.
5. WHEN сообщение успешно сохранено, THE Messaging_Service SHALL отправить отправителю подтверждение доставки на сервер (статус «отправлено»).
6. WHEN получатель открывает чат и видит сообщение, THE Messaging_Service SHALL отправить отправителю подтверждение прочтения (статус «прочитано»).

### Requirement 8: Индикатор набора текста и присутствия

**User Story:** Как пользователь, я хочу видеть, когда собеседник в сети и набирает сообщение, чтобы понимать ритм диалога.

#### Acceptance Criteria

1. WHEN пользователь начинает вводить текст в поле сообщения, THE NOCTIS_App SHALL отправлять событие `typing_start` не чаще одного раза в 3 секунды.
2. WHEN пользователь прекращает ввод более чем на 5 секунд или отправляет сообщение, THE NOCTIS_App SHALL отправлять событие `typing_stop`.
3. WHEN Presence_Service получает событие `typing_start` для Direct_Chat, THE Presence_Service SHALL ретранслировать его собеседнику в течение 200 миллисекунд.
4. WHILE пользователь подключён по WebSocket, THE Presence_Service SHALL помечать его статус как «онлайн».
5. WHEN пользователь отключается от WebSocket, THE Presence_Service SHALL пометить статус как «офлайн» и сохранить временную метку «был в сети» в течение 5 секунд.
6. WHERE пользователь скрыл время последнего посещения в настройках приватности, THE Presence_Service SHALL возвращать другим пользователям обобщённое значение («недавно», «на этой неделе», «давно») вместо точного времени.

### Requirement 9: История сообщений и пагинация

**User Story:** Как пользователь, я хочу прокручивать историю переписки и быстро находить старые сообщения, чтобы возвращаться к важным темам.

#### Acceptance Criteria

1. WHEN пользователь открывает чат, THE NOCTIS_App SHALL загружать последние 50 сообщений в течение 800 миллисекунд при стабильном соединении.
2. WHEN пользователь прокручивает вверх и достигает верхней границы загруженных сообщений, THE NOCTIS_App SHALL запрашивать следующие 50 сообщений до достижения начала чата.
3. THE Messaging_Service SHALL хранить историю Direct_Chat без ограничения по времени, пока пользователь не удалил сообщения вручную.
4. WHEN пользователь выполняет полнотекстовый поиск по сообщениям чата, THE Messaging_Service SHALL возвращать релевантные результаты в течение 1500 миллисекунд для чата объёмом до 100 000 сообщений.

### Requirement 10: Редактирование и удаление сообщений

**User Story:** Как пользователь, я хочу редактировать и удалять отправленные сообщения, чтобы исправлять ошибки и отзывать неактуальные сообщения.

#### Acceptance Criteria

1. WHEN пользователь редактирует своё текстовое сообщение в течение 48 часов после отправки, THE Messaging_Service SHALL обновить содержимое сообщения и пометить его флагом `edited`.
2. IF пользователь пытается отредактировать сообщение, отправленное более 48 часов назад, THEN THE Messaging_Service SHALL вернуть ошибку `EDIT_WINDOW_EXPIRED`.
3. WHEN пользователь удаляет сообщение «только у себя», THE NOCTIS_App SHALL скрыть сообщение локально, а THE Messaging_Service SHALL сохранить его для остальных участников.
4. WHEN пользователь удаляет сообщение «у всех», THE Messaging_Service SHALL удалить содержимое сообщения у всех участников Direct_Chat в течение 2 секунд.
5. WHEN сообщение отредактировано, THE NOCTIS_App SHALL отображать метку «изменено» рядом с временем сообщения.

### Requirement 11: Исчезающие сообщения

**User Story:** Как пользователь, я хочу включать автоудаление сообщений в чате, чтобы не оставлять лишнюю переписку на устройствах.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL позволять выбирать TTL для исчезающих сообщений из значений: 5 секунд, 30 секунд, 1 минута, 1 час, 24 часа, 7 суток, 30 суток.
2. WHEN пользователь включает исчезающие сообщения с заданным TTL, THE Messaging_Service SHALL присваивать всем последующим сообщениям в этом чате выбранное значение TTL.
3. WHEN получатель прочитал Disappearing_Message, THE Messaging_Service SHALL запустить таймер удаления и удалить сообщение у всех участников по истечении TTL с точностью ±2 секунды.
4. WHEN отправитель меняет TTL для чата, THE Messaging_Service SHALL применять новое значение только к сообщениям, отправленным после изменения.
5. THE NOCTIS_App SHALL отображать индикатор обратного отсчёта рядом с каждым Disappearing_Message.

### Requirement 12: Секретные чаты со сквозным шифрованием

**User Story:** Как пользователь, заботящийся о приватности, я хочу вести секретные чаты со сквозным шифрованием, чтобы только я и собеседник могли читать сообщения.

#### Acceptance Criteria

1. WHEN пользователь создаёт Secret_Chat с другим пользователем, THE Crypto_Module SHALL выполнить протокол X3DH для согласования начального общего секрета.
2. WHEN сообщение отправляется в Secret_Chat, THE Crypto_Module SHALL шифровать его по алгоритму Double Ratchet перед передачей серверу.
3. THE NOCTIS_Backend SHALL хранить сообщения Secret_Chat исключительно в зашифрованном виде и не иметь доступа к ключам шифрования.
4. THE Secret_Chat SHALL быть привязан к конкретному устройству и не синхронизироваться между устройствами одной учётной записи.
5. THE NOCTIS_App SHALL отображать отпечаток ключа шифрования и QR-код для проверки идентичности собеседника.
6. IF отпечаток ключа изменился между сессиями, THEN THE NOCTIS_App SHALL отображать предупреждение о возможной атаке посредника.
7. THE Secret_Chat SHALL поддерживать исчезающие сообщения и запрещать пересылку сообщений в обычные чаты.

### Requirement 13: Отправка медиафайлов

**User Story:** Как пользователь, я хочу отправлять фото, видео, документы и голосовые сообщения, чтобы делиться разнообразным контентом.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL поддерживать отправку файлов размером до 2048 МБ.
2. WHEN пользователь отправляет изображение, THE NOCTIS_App SHALL сжимать его до максимального размера 2560 пикселей по длинной стороне с качеством JPEG 85, если включено сжатие.
3. WHEN пользователь отправляет файл, THE Media_Service SHALL загружать его частями (chunked upload) и поддерживать возобновление прерванной загрузки.
4. WHEN загрузка медиа завершена, THE Media_Service SHALL вычислить SHA-256 файла и вернуть постоянный URL в течение 2 секунд после получения последнего чанка.
5. WHEN пользователь отправляет голосовое сообщение, THE NOCTIS_App SHALL кодировать его в формат Opus с битрейтом 32 кбит/с.
6. WHEN получатель воспроизводит видео или голосовое сообщение, THE Media_Service SHALL поддерживать потоковую передачу с поддержкой HTTP Range Requests.

### Requirement 14: Голосовые сообщения с транскрибацией

**User Story:** Как пользователь, я хочу видеть текстовую расшифровку голосовых сообщений, чтобы быстро понимать содержание без прослушивания.

#### Acceptance Criteria

1. WHEN получатель открывает голосовое сообщение и запрашивает транскрибацию, THE Media_Service SHALL возвращать текстовую расшифровку в течение 10 секунд для сообщений длительностью до 60 секунд.
2. WHERE язык голосового сообщения определён, THE Media_Service SHALL отображать расшифровку с указанием уровня уверенности от 0 до 1.
3. THE NOCTIS_App SHALL отображать визуализацию аудиоволны для каждого голосового сообщения.
4. THE NOCTIS_App SHALL позволять воспроизведение голосового сообщения со скоростью 1.0×, 1.5× и 2.0×.

### Requirement 15: Голосовые и видеозвонки

**User Story:** Как пользователь, я хочу совершать голосовые и видеозвонки внутри мессенджера, чтобы общаться без переключения на другие приложения.

#### Acceptance Criteria

1. WHEN пользователь инициирует голосовой или видеозвонок, THE Call_Service SHALL установить WebRTC-соединение с использованием STUN/TURN-серверов в течение 3 секунд при стабильном соединении.
2. THE Call_Service SHALL шифровать медиапоток по протоколу SRTP с обменом ключами через DTLS.
3. WHEN качество соединения падает ниже 200 кбит/с, THE NOCTIS_App SHALL автоматически снижать разрешение видео до 360p и битрейт до 150 кбит/с.
4. THE NOCTIS_App SHALL поддерживать переключение между фронтальной и основной камерой во время видеозвонка без разрыва соединения.
5. THE NOCTIS_App SHALL поддерживать отключение микрофона, отключение камеры и переключение динамика во время звонка.
6. WHEN звонок завершается, THE Call_Service SHALL сохранять запись о звонке (длительность, тип, статус) в истории чата в течение 1 секунды.

### Requirement 16: Push-уведомления

**User Story:** Как пользователь, я хочу получать уведомления о новых сообщениях и звонках, когда приложение неактивно, чтобы не пропускать важное.

#### Acceptance Criteria

1. WHEN пользователь регистрирует устройство, THE NOCTIS_App SHALL передавать FCM- или APNs-токен в Notification_Service в течение 5 секунд после получения от платформы.
2. WHEN получено новое сообщение для пользователя, не подключённого по WebSocket, THE Notification_Service SHALL отправлять push-уведомление в течение 2 секунд.
3. WHERE пользователь включил «тихие уведомления» для конкретного чата, THE Notification_Service SHALL отправлять push без звука и вибрации.
4. WHERE пользователь установил расписание «не беспокоить» с указанным временным интервалом, THE Notification_Service SHALL не отправлять push-уведомления в этот интервал, кроме сообщений от помеченных «важных» контактов.
5. WHEN пользователь отключает уведомления для чата, THE Notification_Service SHALL прекращать отправку push для этого чата в течение 5 секунд.
6. THE Notification_Service SHALL не включать содержимое сообщений Secret_Chat в тело push-уведомления.

### Requirement 17: Умные теги и категоризация чатов

**User Story:** Как пользователь, я хочу автоматически и вручную помечать чаты тегами, чтобы быстро их находить и фильтровать.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL позволять пользователю создавать пользовательские Smart_Tag с названием длиной от 1 до 24 символов.
2. WHEN пользователь применяет Smart_Tag к чату, THE NOCTIS_Backend SHALL сохранить связь чат–тег в течение 1 секунды и синхронизировать её на все устройства учётной записи.
3. WHERE включён режим автоматической категоризации, THE NOCTIS_App SHALL автоматически предлагать теги «Работа», «Семья», «Друзья», «Финансы», «Путешествия» на основе анализа метаданных чата.
4. THE NOCTIS_App SHALL позволять фильтровать список чатов по одному или нескольким Smart_Tag одновременно.
5. WHEN пользователь удаляет Smart_Tag, THE NOCTIS_Backend SHALL удалить тег и все его связи с чатами в течение 2 секунд.

### Requirement 18: Папки чатов и закрепление

**User Story:** Как пользователь с большим количеством чатов, я хочу организовывать их в папки и закреплять важные, чтобы быстрее ориентироваться в списке.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL позволять создавать до 20 пользовательских папок чатов.
2. WHEN пользователь добавляет чат в папку, THE NOCTIS_Backend SHALL синхронизировать состав папки на все устройства учётной записи в течение 2 секунд.
3. THE NOCTIS_App SHALL позволять закреплять до 10 чатов в каждой папке.
4. THE NOCTIS_App SHALL отображать закреплённые чаты в верхней части списка с визуальным индикатором закрепления.
5. WHEN пользователь применяет фильтр папки «Непрочитанные», THE NOCTIS_App SHALL отображать только чаты с непрочитанными сообщениями.

### Requirement 19: Поиск по сообщениям, контактам и медиа

**User Story:** Как пользователь, я хочу искать по всем своим данным, чтобы быстро находить нужное.

#### Acceptance Criteria

1. WHEN пользователь вводит поисковый запрос длиной от 2 символов, THE NOCTIS_App SHALL отображать результаты по контактам, чатам, сообщениям и медиа в течение 1500 миллисекунд.
2. THE Messaging_Service SHALL поддерживать полнотекстовый поиск с морфологией для русского и английского языков.
3. THE NOCTIS_App SHALL позволять фильтровать результаты поиска по типу: «Сообщения», «Контакты», «Медиа», «Файлы», «Ссылки».
4. WHEN пользователь выбирает результат поиска по сообщению, THE NOCTIS_App SHALL открывать чат и прокручивать к найденному сообщению с подсветкой совпадения.

### Requirement 20: Реакции и ответы

**User Story:** Как пользователь, я хочу реагировать эмодзи и отвечать на конкретные сообщения, чтобы вести более структурированный диалог.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL позволять добавлять реакцию из набора 32 предустановленных эмодзи к любому сообщению.
2. WHEN пользователь добавляет реакцию, THE Messaging_Service SHALL ретранслировать её всем участникам чата в течение 500 миллисекунд.
3. THE NOCTIS_App SHALL позволять отвечать на конкретное сообщение с цитатой исходного сообщения.
4. WHEN пользователь нажимает на цитату в ответе, THE NOCTIS_App SHALL прокручивать чат к исходному сообщению.
5. THE NOCTIS_App SHALL позволять убирать ранее добавленную реакцию одним нажатием.

### Requirement 21: Пересылка сообщений

**User Story:** Как пользователь, я хочу пересылать сообщения другим контактам, чтобы делиться информацией.

#### Acceptance Criteria

1. WHEN пользователь пересылает сообщение в другой чат, THE Messaging_Service SHALL сохранять метку «переслано от» с указанием исходного автора, если автор не скрыл это в настройках приватности.
2. WHERE автор исходного сообщения скрыл свой профиль для пересылок, THE Messaging_Service SHALL отображать метку «переслано» без указания автора.
3. THE Secret_Chat SHALL запрещать пересылку сообщений из секретного чата в любой другой чат.
4. THE NOCTIS_App SHALL позволять пересылать до 100 сообщений за одну операцию.

### Requirement 22: Черновики сообщений

**User Story:** Как пользователь, я хочу, чтобы недописанные сообщения сохранялись и были доступны на всех моих устройствах, чтобы не терять текст.

#### Acceptance Criteria

1. WHEN пользователь покидает чат, не отправив набранный текст, THE NOCTIS_App SHALL сохранять черновик локально в течение 1 секунды.
2. WHEN черновик длиной более 0 символов изменяется, THE NOCTIS_Backend SHALL синхронизировать его на другие устройства учётной записи не позднее чем через 5 секунд.
3. WHEN пользователь отправляет черновик или удаляет его содержимое, THE NOCTIS_Backend SHALL удалить черновик на всех устройствах в течение 2 секунд.

### Requirement 23: Стикеры и кастомные наборы

**User Story:** Как пользователь, я хочу отправлять стикеры и создавать собственные наборы, чтобы выражать эмоции в монохромном стиле.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL поставляться с не менее чем 5 встроенными монохромными наборами стикеров.
2. THE NOCTIS_App SHALL поддерживать импорт стикеров в форматах WebP и Lottie размером до 512 КБ на стикер.
3. WHEN пользователь создаёт пользовательский набор стикеров, THE Media_Service SHALL сохранять набор и предоставлять ссылку для приглашения других пользователей.
4. WHEN пользователь добавляет стикер по ссылке-приглашению, THE NOCTIS_Backend SHALL добавить набор в коллекцию пользователя в течение 2 секунд.

### Requirement 24: Мини-инструменты внутри чата

**User Story:** Как пользователь, я хочу использовать встроенные мини-инструменты, чтобы выполнять частые задачи без выхода из чата.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL предоставлять Mini_Tool для калькулятора с поддержкой базовых операций.
2. THE NOCTIS_App SHALL предоставлять Mini_Tool для конвертера валют с обновлением курсов не реже одного раза в 24 часа.
3. THE NOCTIS_App SHALL предоставлять Mini_Tool для конвертера единиц измерения (длина, масса, температура, объём).
4. THE NOCTIS_App SHALL предоставлять Mini_Tool для таймера и секундомера с точностью 100 миллисекунд.
5. THE NOCTIS_App SHALL предоставлять Mini_Tool для переводчика текста между русским, английским, испанским, немецким, французским и китайским языками.
6. THE NOCTIS_App SHALL предоставлять Mini_Tool для разделения счёта между участниками чата.
7. THE NOCTIS_App SHALL предоставлять Mini_Tool для генератора QR-кодов из произвольного текста.
8. THE NOCTIS_App SHALL предоставлять Mini_Tool для голосования (poll) с открытыми и анонимными результатами.
9. WHEN результат Mini_Tool отправляется в чат, THE NOCTIS_App SHALL форматировать его как обычное сообщение с указанием источника инструмента.

### Requirement 25: Запланированные и напоминающие сообщения

**User Story:** Как пользователь, я хочу планировать отправку сообщений и устанавливать напоминания, чтобы управлять временем коммуникации.

#### Acceptance Criteria

1. WHEN пользователь устанавливает запланированное время отправки сообщения, THE Messaging_Service SHALL отправить сообщение в указанное время с точностью ±5 секунд.
2. WHERE запланированное время в прошлом, THE NOCTIS_App SHALL не позволять подтвердить планирование и отображать ошибку валидации.
3. THE NOCTIS_App SHALL позволять пользователю редактировать или отменять запланированное сообщение до момента его отправки.
4. WHEN пользователь устанавливает напоминание о сообщении на конкретное время, THE Notification_Service SHALL отправить локальное напоминание с точностью ±5 секунд.

### Requirement 26: Цитирование и пересылка с комментарием

**User Story:** Как пользователь, я хочу пересылать сообщения с собственным комментарием, чтобы добавлять контекст.

#### Acceptance Criteria

1. WHEN пользователь пересылает сообщение, THE NOCTIS_App SHALL позволять прикрепить текстовый комментарий длиной до 4096 символов.
2. THE NOCTIS_App SHALL отображать пересланное сообщение и комментарий как единое сообщение в чате.
3. WHEN пересылается несколько сообщений, THE NOCTIS_App SHALL группировать их в одно сообщение с комментарием.

### Requirement 27: Отметки прочтения и доставки

**User Story:** Как пользователь, я хочу видеть, доставлено и прочитано ли моё сообщение, чтобы понимать состояние коммуникации.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL отображать статус сообщения одной из меток: «отправляется», «отправлено», «доставлено», «прочитано», «не доставлено».
2. WHEN получатель открывает чат и видит сообщение, THE Messaging_Service SHALL отправлять отправителю статус «прочитано» в течение 500 миллисекунд.
3. WHERE получатель отключил отправку отметок прочтения в настройках приватности, THE Messaging_Service SHALL не отправлять отправителю статус «прочитано».

### Requirement 28: Архивирование чатов

**User Story:** Как пользователь, я хочу скрывать неактуальные чаты в архив, чтобы поддерживать порядок в основном списке.

#### Acceptance Criteria

1. WHEN пользователь архивирует чат, THE NOCTIS_App SHALL переносить его в раздел «Архив» в течение 1 секунды.
2. WHEN в архивированный чат приходит новое сообщение, THE NOCTIS_App SHALL автоматически возвращать чат в основной список, если включена опция «возвращать из архива».
3. THE NOCTIS_App SHALL позволять отключить автоматическое возвращение чата из архива при новых сообщениях.

### Requirement 29: Закладки и сохранённые сообщения

**User Story:** Как пользователь, я хочу сохранять важные сообщения, чтобы быстро возвращаться к ним позже.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL предоставлять системный чат «Сохранённые», доступный только владельцу учётной записи.
2. WHEN пользователь сохраняет сообщение в закладки, THE Messaging_Service SHALL копировать содержимое сообщения и медиа-вложения в чат «Сохранённые» в течение 2 секунд.
3. THE NOCTIS_App SHALL позволять группировать сохранённые сообщения по Smart_Tag.

### Requirement 30: Цитаты и форматирование текста

**User Story:** Как пользователь, я хочу форматировать текст сообщений, чтобы делать их структурированными и выразительными.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL поддерживать форматирование текста: жирный, курсив, подчёркнутый, зачёркнутый, моноширинный, спойлер.
2. THE NOCTIS_App SHALL поддерживать вставку блока кода с подсветкой синтаксиса для не менее чем 30 языков программирования.
3. WHEN пользователь использует синтаксис Markdown в сообщении, THE NOCTIS_App SHALL отображать форматированный результат с возможностью просмотра исходного текста.
4. THE NOCTIS_App SHALL поддерживать вставку гиперссылок и автоматическое распознавание URL.

### Requirement 31: Предпросмотр ссылок

**User Story:** Как пользователь, я хочу видеть предпросмотр содержимого ссылок, чтобы понимать, на что я перехожу.

#### Acceptance Criteria

1. WHEN сообщение содержит URL, THE Messaging_Service SHALL получать метаданные Open Graph и возвращать заголовок, описание и миниатюру в течение 3 секунд.
2. WHERE URL ведёт на запрещённый или недоступный ресурс, THE Messaging_Service SHALL не возвращать предпросмотр и не блокировать отправку сообщения.
3. THE NOCTIS_App SHALL позволять пользователю отключить генерацию предпросмотра для конкретного сообщения перед отправкой.

### Requirement 32: Геолокация

**User Story:** Как пользователь, я хочу отправлять текущее или живое местоположение, чтобы делиться им с собеседником.

#### Acceptance Criteria

1. WHEN пользователь отправляет статичное местоположение, THE NOCTIS_App SHALL прикреплять координаты с точностью не хуже 50 метров и миниатюру карты.
2. WHEN пользователь включает «живую геолокацию» на 15, 60 или 480 минут, THE NOCTIS_App SHALL обновлять координаты на сервере не реже одного раза в 60 секунд.
3. WHEN истекает срок действия живой геолокации или пользователь её останавливает, THE NOCTIS_App SHALL прекращать отправку обновлений в течение 5 секунд.

### Requirement 33: Контакты и визитные карточки

**User Story:** Как пользователь, я хочу отправлять контактные данные другого пользователя или внешний контакт в виде vCard, чтобы делиться информацией о людях.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL позволять прикреплять контакт из адресной книги в виде vCard.
2. WHEN получатель нажимает на контакт vCard, THE NOCTIS_App SHALL предлагать сохранить контакт или начать чат при наличии учётной записи NOCTIS у этого контакта.

### Requirement 34: Опросы и викторины

**User Story:** Как пользователь, я хочу создавать опросы и викторины, чтобы собирать мнения и проводить активности.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL позволять создавать опрос с вопросом длиной до 256 символов и от 2 до 10 вариантов ответа.
2. THE NOCTIS_App SHALL поддерживать режим «викторина» с одним правильным ответом и текстом-объяснением.
3. THE NOCTIS_App SHALL поддерживать режим «множественный выбор» и анонимный режим голосования.
4. WHEN участник голосует, THE Messaging_Service SHALL обновлять результаты у всех участников в течение 1 секунды.

### Requirement 35: Приватность и блокировка пользователей

**User Story:** Как пользователь, я хочу блокировать нежелательных собеседников и контролировать, кто видит мои данные, чтобы защищать своё пространство.

#### Acceptance Criteria

1. WHEN пользователь блокирует другого пользователя, THE Messaging_Service SHALL прекращать доставку сообщений от заблокированного пользователя в течение 1 секунды.
2. WHERE пользователь заблокирован, THE Presence_Service SHALL не сообщать ему статус «онлайн», «был в сети» и индикатор набора текста инициатора блокировки.
3. THE NOCTIS_App SHALL позволять настраивать, кто может видеть номер телефона: «все», «контакты», «никто».
4. THE NOCTIS_App SHALL позволять настраивать, кто может видеть аватар: «все», «контакты», «никто».
5. THE NOCTIS_App SHALL позволять настраивать, кто может звонить пользователю: «все», «контакты», «никто».
6. THE NOCTIS_App SHALL позволять настраивать, кто может пересылать сообщения от пользователя: «все», «контакты», «никто».

### Requirement 36: Жалобы и модерация

**User Story:** Как пользователь, я хочу сообщать о нарушениях, чтобы поддерживать безопасную среду.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL предоставлять функцию жалобы на сообщение или пользователя с категориями: «Спам», «Мошенничество», «Угрозы», «Откровенный контент», «Другое».
2. WHEN пользователь отправляет жалобу, THE NOCTIS_Backend SHALL регистрировать её в системе модерации в течение 5 секунд.
3. WHERE жалоба касается Secret_Chat, THE NOCTIS_App SHALL не передавать содержимое сообщений на сервер модерации.

### Requirement 37: Экспорт и резервное копирование

**User Story:** Как пользователь, я хочу экспортировать историю чатов, чтобы создавать локальные резервные копии.

#### Acceptance Criteria

1. WHEN пользователь запрашивает экспорт чата, THE NOCTIS_App SHALL формировать архив в формате JSON или HTML с прикреплёнными медиафайлами.
2. THE NOCTIS_App SHALL шифровать локальный архив с помощью пароля, заданного пользователем, по алгоритму AES-256-GCM.
3. THE NOCTIS_App SHALL позволять выбирать диапазон дат для экспорта.

### Requirement 38: Удаление учётной записи

**User Story:** Как пользователь, я хочу удалить свою учётную запись, чтобы стереть свои данные из сервиса.

#### Acceptance Criteria

1. WHEN пользователь подтверждает удаление учётной записи, THE Auth_Service SHALL пометить учётную запись как удалённую и инвалидировать все сессии в течение 5 секунд.
2. THE NOCTIS_Backend SHALL удалять профильные данные, сообщения и медиафайлы пользователя не позднее чем через 30 суток после подтверждения удаления.
3. THE Auth_Service SHALL предоставлять опцию автоматического удаления учётной записи при отсутствии активности в течение 30, 90, 180 или 365 суток.

### Requirement 39: Монохромная цветовая палитра

**User Story:** Как пользователь, ценящий минимализм, я хочу видеть строго монохромный интерфейс, чтобы получать визуально чистый опыт.

#### Acceptance Criteria

### Requirement 40: Микроинтеракции и анимации 60fps

**User Story:** Как пользователь, я хочу видеть плавные микроинтеракции при каждом действии, чтобы получать премиальное ощущение от приложения.

6. WHERE пользователь включил настройку «Уменьшить движение», THE UI_Engine SHALL заменять анимации на мгновенные переходы или статичные кросс-фейды длительностью не более 100 миллисекунд.

### Requirement 41: Типографика и иконография

**User Story:** Как пользователь, я хочу видеть последовательную премиальную типографику и иконки, чтобы интерфейс выглядел целостным.

### Requirement 42: Тактильная обратная связь

**User Story:** Как пользователь, я хочу ощущать тактильную обратную связь при ключевых действиях, чтобы взаимодействие было осязаемым.

3. WHEN происходит ошибка действия, THE UI_Engine SHALL воспроизводить тактильный отклик «ошибка».

### Requirement 43: Доступность

**User Story:** Как пользователь со специальными потребностями, я хочу пользоваться мессенджером с программами чтения экрана и крупным шрифтом, чтобы получать равный доступ.

#### Acceptance Criteria

### Requirement 45: Локальное хранение и оффлайн-режим

### Requirement 46: Биометрический вход

**User Story:** Как пользователь, я хочу защищать вход в приложение биометрией, чтобы посторонние не могли прочитать переписку.

### Requirement 47: Бэкенд на Go

**User Story:** Как разработчик, я хочу высокопроизводительный бэкенд, чтобы обрабатывать большое количество одновременных WebSocket-соединений.

4. THE NOCTIS_Backend SHALL предоставлять конечную точку проверки работоспособности `/healthz`, возвращающую HTTP 200 при работоспособном состоянии.

### Requirement 48: PostgreSQL для постоянного хранения

**User Story:** Как разработчик, я хочу надёжное хранилище для пользовательских данных и истории сообщений, чтобы не терять данные.

### Requirement 49: Redis для presence и pub/sub

**User Story:** Как разработчик, я хочу низколатентное хранилище для онлайн-статусов и шину сообщений между инстансами, чтобы поддерживать реалтайм.

#### Acceptance Criteria

2. THE Presence_Service SHALL хранить онлайн-статусы пользователей в Redis с TTL 90 секунд.
3. THE Messaging_Service SHALL использовать Redis Pub/Sub или Redis Streams для маршрутизации сообщений между инстансами `NOCTIS_Backend`.
4. THE Auth_Service SHALL хранить refresh-токены и счётчики попыток в Redis с настроенным TTL.

### Requirement 50: API-документация

**User Story:** Как разработчик, я хочу актуальную документацию API, чтобы понимать контракт между клиентом и сервером.

### Requirement 51: Производительность сервера

**User Story:** Как пользователь, я хочу мгновенный отклик от сервера, чтобы общение было живым.

#### Acceptance Criteria

2. THE Auth_Service SHALL обрабатывать 95% запросов выдачи токенов за время не более 300 миллисекунд при нагрузке до 200 запросов в секунду на инстанс.
3. THE Media_Service SHALL обеспечивать пропускную способность загрузки медиа не менее 50 МБ/с на инстанс при наличии достаточной пропускной способности сети.

### Requirement 52: Логирование и наблюдаемость

**User Story:** Как разработчик, я хочу подробные логи и метрики, чтобы быстро диагностировать проблемы в продакшене.

#### Acceptance Criteria

3. THE NOCTIS_Backend SHALL поддерживать корреляцию логов через `request_id`, передаваемый клиентом в заголовке `X-Request-ID`.

### Requirement 53: Безопасность транспорта

**User Story:** Как пользователь, я хочу, чтобы все данные передавались по защищённому каналу, чтобы их нельзя было перехватить.

#### Acceptance Criteria

3. THE NOCTIS_App SHALL отклонять соединения с сервером при недействительном или отозванном сертификате.

### Requirement 54: Защита от перебора и злоупотреблений

**User Story:** Как владелец сервиса, я хочу ограничивать частоту запросов, чтобы защититься от перебора и злоупотреблений.

#### Acceptance Criteria

2. THE Messaging_Service SHALL ограничивать отправку сообщений до 30 сообщений в секунду от одной учётной записи.
3. IF клиент превышает установленный лимит, THEN THE NOCTIS_Backend SHALL возвращать HTTP 429 с заголовком `Retry-After`.

### Requirement 55: GitHub Actions для сборки APK

**User Story:** Как разработчик, я хочу автоматическую сборку Android APK при пуше в `main`, чтобы получать готовый артефакт без ручных действий.

#### Acceptance Criteria

4. IF любая из команд `flutter analyze` или `flutter test` завершается с ошибкой, THEN THE CI_Pipeline SHALL прекращать выполнение workflow и помечать сборку как неуспешную.
5. THE CI_Pipeline SHALL собирать релизный APK командой `flutter build apk --release`.
6. THE CI_Pipeline SHALL подписывать APK ключом, хранящимся в секретах репозитория `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.

### Requirement 56: Публикация APK в GitHub Releases

#### Acceptance Criteria

### Requirement 57: Качество и тестирование в CI

### Requirement 58: Provision-скрипт VPS

**User Story:** Как DevOps-инженер, я хочу один Bash-скрипт для подготовки чистого VPS Ubuntu 22, чтобы быстро развернуть NOCTIS_Backend на новом сервере.

#### Acceptance Criteria

3. THE Provision_Script SHALL устанавливать Docker Engine и Docker Compose plugin последних стабильных версий из официальных репозиториев Docker.
4. THE Provision_Script SHALL устанавливать Nginx и настраивать обратный прокси для портов `80` и `443` на внутренний порт NOCTIS_Backend.
5. THE Provision_Script SHALL устанавливать `certbot` и получать TLS-сертификат Let's Encrypt для указанного доменного имени.
6. THE Provision_Script SHALL запускать контейнеры PostgreSQL 15 и Redis 7 через Docker Compose с томами для постоянных данных.

10. IF любая из команд установки или запуска контейнеров завершается с ошибкой, THEN THE Provision_Script SHALL прекращать выполнение, выводить сообщение об ошибке и возвращать ненулевой код выхода.
11. THE Provision_Script SHALL быть идемпотентным: повторный запуск на уже подготовленном VPS SHALL не приводить к ошибкам и не дублировать конфигурации.

### Requirement 59: Среда выполнения и переменные окружения

**User Story:** Как DevOps-инженер, я хочу управлять конфигурацией NOCTIS_Backend через переменные окружения, чтобы переносить деплой между средами.

#### Acceptance Criteria

3. THE NOCTIS_Backend SHALL поддерживать перезагрузку конфигурации логирования по сигналу `SIGHUP` без перезапуска процесса.

### Requirement 60: Развёртывание через Docker Compose

**User Story:** Как DevOps-инженер, я хочу развёртывать стек одной командой Docker Compose, чтобы упростить эксплуатацию.

#### Acceptance Criteria

### Requirement 61: Мониторинг и алерты

**User Story:** Как DevOps-инженер, я хочу видеть состояние системы и получать алерты, чтобы реагировать на инциденты.

#### Acceptance Criteria

1. THE NOCTIS_Backend SHALL экспортировать метрики Prometheus на конечной точке `/metrics`.

### Requirement 62: Резервное копирование

**User Story:** Как DevOps-инженер, я хочу автоматические бэкапы базы данных, чтобы восстанавливать сервис после сбоев.

#### Acceptance Criteria

### Requirement 63: Парсер и сериализатор сетевых сообщений

**User Story:** Как разработчик, я хочу надёжный парсер и сериализатор формата сообщений между клиентом и сервером, чтобы исключить расхождения протокола.

#### Acceptance Criteria

1. THE NOCTIS_Backend SHALL предоставлять парсер JSON-сообщений WebSocket-протокола, валидирующий типы событий и обязательные поля по схеме JSON Schema.
2. THE NOCTIS_Backend SHALL предоставлять сериализатор, формирующий сообщения WebSocket-протокола, проходящие валидацию по той же JSON Schema.
3. FOR ALL валидных сообщений WebSocket-протокола парсинг с последующей сериализацией и повторным парсингом SHALL давать эквивалентное представление (свойство round-trip).
4. IF сообщение не соответствует JSON Schema, THEN THE NOCTIS_Backend SHALL возвращать клиенту ошибку `PROTOCOL_VALIDATION_FAILED` с описанием первого нарушения.

### Requirement 64: Парсер форматирования сообщений

**User Story:** Как разработчик, я хочу единый парсер форматированного текста (Markdown-подмножество), чтобы клиент и сервер одинаково интерпретировали разметку.

#### Acceptance Criteria

1. THE NOCTIS_App SHALL парсить форматированный текст в дерево узлов с типами `bold`, `italic`, `underline`, `strikethrough`, `monospace`, `spoiler`, `code_block`, `link`, `mention`, `hashtag`.
2. THE NOCTIS_App SHALL предоставлять сериализатор дерева узлов обратно в исходный текст разметки.
3. FOR ALL валидных деревьев форматирования сериализация с последующим парсингом SHALL давать эквивалентное дерево (свойство round-trip).
4. IF текст содержит синтаксическую ошибку разметки, THEN THE NOCTIS_App SHALL отображать сырой текст без форматирования и не блокировать отправку.
